# Testing the DSP library

Two kinds of evidence protect the port: **differential tests** (does the port behave exactly like the blob?) and the **O0 identity check**
(did a restructuring change any code at all?).  Behaviour changes need the first; pure restructuring (moves, renames, macro spellings,
struct conversions) is gated by the second, which is cheap and needs no test run.

## Differential tests (blob vs port)

One job per `test/build_and_diff_<id>.sh` (ids are the porting chunks: `p01` - `p47`, `v01` - `v07`, `z01`, `r02` - `r31`, the V.34 tiers
`v34_tier*`, `v32*`, `v8*`, `fpm`, `b103`, `v23`, `rd`, ...; 183 jobs in all).  A script builds, as 32-bit programs, the SAME harness main
(`test/<id>_diff_main.c`, library `test/harness/`) twice: once linked with the blob oracle (`$BLOB_O`: `../dsplibs.o` unless the environment says otherwise; the ONE place that names it is `test/blob.sh`, read by the python tools through `tools/blobpath.py`), once with the port's sources, and runs every
scenario in its own process:

* the function under test is real on both sides; its callees are usually **recorders** (harness functions that log their arguments and
  return scripted values), so a chunk is compared in isolation; end-to-end jobs (`*_e2e`, `*_eng`, `*_integ`) use the real callees instead;
* the output (object dumps through the layout mirrors of `test/<chunk>.layout`, recorder logs, hashes of sample streams) must be identical:
  the script prints `MATCH`.  Most chunks also compare an **independent model** (C written from the disassembly, not from the port) and require
  **coverage** of every branch site they claim;
* the port is built at `-O0` and `-O2`, plain and with the pinned flags of `test/flags.sh` (`-fno-strict-aliasing`; stage "1p" through
  `test/flagshim/`), and the blob's recorded output is the **golden** for the x86-64 stage: `test/<id>_golden64.sh` or the generic
  `test/tier_golden64.sh <id>` rebuild the port with `gcc -m64` (no blob) and compare with `test/golden/<id>_blob32.out(.gz)`; known x86-64
  differences are listed, scenario by scenario, in `test/golden/tier_golden64_xfail.txt`.

Mutation testing (`tools/mutate.py`) checked, chunk by chunk, that the tests notice code changes (every surviving mutant is analysed in the
journal).  End-to-end: two real slmodemd instances over the repository's nullmodem (`test/n01_matrix.py`), the virtual-clock record / replay
oracle (`test/n02_*`), the fax and voice drivers (`test/x3_fax_pair.py`, `test/r17_voice_smoke.py`); they need built binaries and real time
and are not run_changed jobs.  `docs/bugs.md` is the register of every defect these tests found.

## run_changed.sh

`sh tools/run_changed.sh [-j N] [--g64] [id ...]` runs the jobs whose inputs changed since they last passed.  The key of a job is a sha256 over
the compiler version, the script, every file the script names (followed recursively), the files of its chunk tokens (`test/<tok>_*`,
`test/golden/<tok>_*` and the library files listed for the token in `test/libfiles_by_token.txt`) and the `gcc -MM` closure of every source
among them; a stamp (`test/.stamps/<id>`) is written only after the job passed.  `--dry-run` lists what would run, `--keys` prints the keys,
`--list` the jobs and the uncovered scripts, `-j N` runs jobs in private sandbox trees in parallel, `--g64` adds the x86-64 golden stage.
Since the RS4 move every key hashes the new paths: **all stamps recorded before RS4 are invalid**, the next full run runs all 183 jobs.  Use
`--all` only for switch-over-scale changes.

**Since STAMPKEYS (journal section STAMPKEYS) the key is the key of the COMPILED code, not of the library source text** (the description of the key above is
the old `--src-keys` key, still available and still used for the jobs listed below).  A stamp now means *"the same compiled port code (plus the same job
script, harness text and goldens) as a run that passed"*: for every compile unit the job builds (flags recorded from the real script runs, stages 1 / 1p / 1b / 2)
the key hashes what the unit compiles to - per function the bytes with relocations as symbol names, per data object the bytes - as an order-independent
multiset, so a comment edit, a prototype moved into a header (RL4 / RL5) or a function moved between two files of the same job keeps the stamp, and any
change of generated code (a constant, a struct layout, an inline helper, a flag) drops it.  Not covered: address / link-order dependence, harness text (hashed
as text), code a helper script reads at run time but the recorder did not see; `h01_heap` and `x3_v34layout` stay on the source-text key.  `x4_params64` (X64FIX) runs the V90Phase2Info / V92Phase2Info constructors and the V90Resampler against REAL `V90Parameters` / `V92Parameters` objects at the native x86-64 layout (the blob-facing harnesses p05 / p06 keep an i386-image stand-in and map the offsets themselves).  The first run after
the switch re-keys every job once.  Details, options (`--src-keys`, `--keys --key-info`), cache and blind spots: `tools/README.md` "STAMPKEYS".
**State after the end of the strict phase (EOS, journal section EOS):** the first full run since RS1 ran all 183 jobs (`-j 8 --all --g64`: 2,780 s on the base, 5,274 s the second time) and all of them pass; every stamp is current.  Test scripts that compile library sources need `-Isrc` (library headers include `fpm/...`, `core/...`, `v8/...`); 33 scripts lacked it and could not build until EOS.  Facts the run established: a test edit can be wrong at x86-64 only (r19_life: found by stage 2, not by the stage-1 MATCH or the -m32 object identity), so a restructuring that touches test files must be followed by that job's golden64 stage; the goldens v01 .. v07 and x1_flagdiff were re-recorded (the differences are explained in the journal); h01_heap failed once under load (not reproduced).  Reference: tools/README.md (run_changed.sh, tier_golden64.sh).

## Job manifest and aliases (TESTREORG stage 1)

`test/jobs.tsv` lists every job (185 rows, ALL moved since stage 9: the 184 jobs of `run_changed.sh --list` plus `x1_flagdiff`, which run_changed plans itself and `--list` now prints too):
id, src/ module, planned new name (`<module>/<stem of the primary src file>[.<facet>]`), the scripts that run it, its harness files, its goldens, whether it has a
x86-64 stage 2, notes.  The columns are explained in the header of the file.  Nothing reads it to run a job yet; it records what the scripts do today so that the
`test/<module>/` move (survey layout B: flat per module, files named by job stem, goldens in `test/golden/<module>/`, build artifacts in `test/.build/`, ids renamed
last) can proceed one module at a time with `git mv`, updating the rows in the same commit.  `tools/job_aliases.tsv` maps old id -> active id (equal to the old id
in stage 1) -> planned name; `tools/run_changed.sh` resolves its id arguments through `tools/job_resolve.sh`, so `run_changed.sh ring/ring_detector` selects `rd`.
Stamp keys are unchanged (the keys of all 185 jobs are byte-identical before and after).  `sh tools/jobs_check.sh` checks the manifest against the tree, `--list` and
the alias table (no job is run).

## Job ids since TESTREORG stage 10 (ids renamed last)

The active job id is the planned name of `test/jobs.tsv` (`new_name`, no `?`): `ring/ring_detector`, `vpcm/pcm_parameters.main`, `v32/v32_engine.status.o2`, `cross/z01_hybrid` ... The old ids (`rd`, `p07`, `n01_v32status_O2`, `z01_hybrid`) are
the `old_id` column of `tools/job_aliases.tsv` and stay valid on EVERY command line: `run_changed.sh`, `run_job.sh`, `tools/job_path.sh` (hence `cover_chunk.sh`, `mutate.py --chunk`), `test/lib/tier_golden64.sh`, `stampkeys.py` resolve an id through that table
(old id, planned name or active id all give the active id; other tokens pass through).  Where an id is DATA the new id is used: `test/jobs.tsv` (`id` = `new_name`), `test/jobclass.txt`, the lines of `test/golden/tier_golden64_xfail.txt` (their `#` comments keep the old ids:
history), the alias table; `h01_heap`'s `MOVED=` list already held the planned names (they are script stems).  Journal sections and test-script comments keep the old ids.

File names made from an id use the file-safe form **fid = id with every `/` replaced by `__`** (`ring/ring_detector` -> `ring__ring_detector`): stamps `test/.stamps/<fid>`, key logs (`RUN_CHANGED_KEYLOG/<fid>[.g64]`), job logs / `.rc` of a parallel run, sandbox directories, the work files `test/.build/<module>/tg64_<fid>_*` of `tier_golden64.sh`,
`blobcov_<fid>` of `cover_chunk.sh`.  `jobs_check.sh` verifies that no id contains `__` and that the characters are `[A-Za-z0-9_./]`, so the form is injective.  `--matrix` stamps (`matrix_...`) already escaped every non-alphanumeric.
Lookups in `jobclass.txt` and the xfail list compare the id exactly (awk), not as a regular expression (the `.` of an id is not a wildcard).

**Stamps are not migrated.**  `test/.stamps/` is ignored by git; the stamps under the old ids (`test/.stamps/rd` ...) are left where they are and are not read: a job under its new id has no stamp, so the first `run_changed.sh` of an id runs it (every key changed with the move anyway).
The first key pass after the rename re-records all 185 recipes (the id is part of the recipe key and of the stage-1b command): about 18 minutes with a cold cache.

## Files of a moved job (TESTREORG stage 2: the convention)

Stage 2 moves the jobs module by module; the pilot is `ring` (job `rd`).  A job is MOVED when the first script of its `test/jobs.tsv` row has a `/`.  The convention, derived from the row's
`new_name` (`<module>/<stem>[.<facet>]`; the job id does not change in this stage):

| file | path |
|---|---|
| stage-1 script (blob vs port, 32-bit) | `test/<module>/<stem>.sh` (replaces `build_and_diff_<id>.sh`; `cd "$(dirname "$0")/../.."`) |
| own stage-2 script, if the job has one | `test/<module>/<stem>.golden64.sh` (replaces `<id>_golden64.sh`) |
| harness main, layout, generated layout files, python checkers | `test/<module>/<stem>.main.c`, `<stem>.layout`, ... next to the script; a header shared by several jobs of the module keeps its own (unique) name in `test/<module>/`; a file shared by jobs of several modules stays in `test/` until all its users move |
| blob golden (the `tier_golden64.sh` case) and its sizes file | `test/golden/<module>/<stem>.blob32.out.gz`, `<stem>.blob32.sizes` (one tree `test/golden`: the sandbox symlink trick is unchanged) |
| build artifacts, work files | `test/.build/<module>/<stem>_*` (`T="${TPREFIX:-test/.build/<module>/<stem>}"` plus `mkdir -p "$(dirname "$T")"`; the script spells T with quotes, `tools/cover_chunk.sh` and the golden update read that line); ONE ignore rule `test/.build/` replaces the per-file lines of `.gitignore` |
| stays in place | `test/flags.sh`, `test/blob.sh`, `test/stub_env*.c`, `test/harness/`, `test/flagshim/`, `test/jobclass.txt`, `test/lib/tier_golden64.sh` (the one generic stage 2; the flat `test/tier_golden64.sh` was deleted by stage 9), `test/golden/tier_golden64_xfail.txt` (keyed by job id) |

The tools find the files of a moved job through `test/jobs.tsv` (`sh tools/job_path.sh ID script|golden64|blob32|sizes|main|module|stem|build|moved`, empty for a job not moved), so one code
path serves moved and not-yet-moved jobs: `run_changed.sh` (job list, stage-2 command, key file lists), `run_job.sh`, `stampkeys.py` (stage 1b recipe), `cover_chunk.sh`, `mutate.py --chunk`.
Stage 2 of a moved job with a blob golden runs `test/lib/tier_golden64.sh`, which reads script / main / golden from the manifest and works in `test/.build/` (it began as a copy of the flat `test/tier_golden64.sh`, whose text was part of the stamp key of every job, so the flat file was left untouched until the last module's move deleted it: stage 9).  `tools/layout_gen.py`, `gen_views.sh`, `params_gen.py`, `member_map.py`, `split_region.py` and
`job_sandbox.sh` needed no change for ring (it has no layout files; the sandbox copies every non-ignored file, so moved files travel with it and `test/golden` stays one symlink); the modules with layout files
change them together with their move.  `jobs_check.sh` enforces the convention for moved rows.

## The O0 identity check (restructuring gate)

`python3 tools/o0check.py [-r REF] [--o2]` (default REF: tag `dsplibs-port-switchover`): every production TU of REF and of the working
tree is built with the exact production recipe (`make -n` of dsplibs-port/Makefile, i.e. `dsplib.mk`; `--via slmodemd` uses slmodemd/Makefile) at `-m32 -O0` and `-m64 -O0`, plus a DWARF
build; it compares every function (objdump, addresses and symbols normalised, relocations resolved), every data section and every struct
layout.  **-m32 -O0 code and i386 layouts must be identical**; -m64 changes are allowed only as reasoned entries of
`tools/o0check_expected.tsv`; `--o2` adds the production i386 -O2 objects as an advisory compare.  TUs moved since REF are paired through
the history map `tools/filemap.tsv` (default `--file-map`).  It proves "same machine code as REF", nothing about behaviour beyond that.
Companions: `tools/ident32.sh` (one file, -O0 / -O2 / pinned, against a git ref), `tools/layoutscan/` (every pair of descriptions of one object
agrees at x86-64), `tools/o0check.py --self-test`.  Reference: tools/README.md sections 15 - 16.

## Compile-only checks used for moves (RS3 / RS4)

* every `test/*.c` / `*.cpp` / `test/harness/*` compiled `-m32 -O0 -c -Isrc -Itest -Itest/harness` before and after: identical objects
  (`objdump -dr` + `objdump -s -r`), the files that need their script's `-D` flags compiled with those flags;
* production `make BITS=32|64` with `SOURCE_DATE_EPOCH` and `LFLAGS=-Wl,--build-id=none`, stripped: byte-identical binaries;
* `run_changed.sh --keys` with `RUN_CHANGED_KEYLOG=DIR` before and after: the same jobs, and (old names through the history map) the same set of
  hashed files per job.
* `sh tools/objcmp.sh <ref>` (RS8): whole objects of two states, function order included, -m32 / -m64 x -O0 / -O2: the check for header moves and de-duplication
  (o0check is blind to the order of the functions inside an object).
* test scripts compile library sources with their own flags: a library source that gains its first path-qualified include (`core/...`) breaks a script that has
  no `-Isrc` (found in RS8: `test/build_and_diff_v34_tier5b.sh`; `..._tier7a.sh` has been unable to compile v34_receiver.c without -Isrc since RS4).
